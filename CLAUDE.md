# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, dependency-free menu-planning webapp. Vocabulary: the **Menu** is the full list of available **Dishes** (`MP_ITEMS`); a **Meal** is Lunch or Dinner, comprising one or more Dishes. You can plan a single meal, a full day (lunch + dinner), or a full work week (Mon-Fri × lunch/dinner), either autogenerated from tag filters and a set of planning rules (see below) or built by hand, picking dishes from a searchable, tagged library with optional images/recipes. No build step, no backend — `MP_ITEMS` in `js/data.js` is the entire "database," and the only persistence is `localStorage`. Deployable to GitHub Pages by committing static files as-is.

### Weekly planning rules

Week-scope autogeneration applies these rules as **best-effort heuristics** — it leans toward satisfying them but never retries/backtracks/fails generation, and there is no in-app warning UI for unsatisfied rules; the user reviews the generated plan and hand-fixes anything off via the picker:

- Monday dinner is vegetarian-only ("meatless Monday").
- Every day has at least one rice-based dish across its lunch+dinner.
- A one-dish-meal dish, once picked for a meal, is paired with exactly one vegetable dish and nothing else.
- Wednesday dinner has a fixed structure: plain rice + a vegetable + a meat-or-fish dish + a soup + one more (any) dish.
- Seafood is a soft dinner preference, not a hard lunch ban.
- Tuesday dinner is hardcoded to "Yong Tau Foo Bee Tai Mak".
- Every meal has either a one-dish meal, or at least one carbohydrate dish among its components.
- No two dishes of the same sub-type (`item.subType`) appear in one meal.
- Lunch is a "quick" meal (tagged `quick`) about 80% of the time — a soft, per-slot probability (`MP_QUICK_LUNCH_PROBABILITY`), not a hard filter.

## Running / testing

No build or test tooling. Open `index.html`, `planner.html`, or `library.html` directly in a browser to try changes; reload to pick them up. There is no `fetch()` of any data file (see below), so opening files directly via `file://` works with no local server needed.

## Architecture

Three pages, each with its own small controller script, sharing common utility scripts loaded before it. All scripts are plain (non-module) `<script src>` includes defining top-level functions/consts as globals — no bundler, no import/export.

- **`js/data.js`** — the menu item master list (`MP_ITEMS`, normally hand-edited directly, or regenerated via `admin.html` — see below) plus shared helpers `getAllTags()`, `getItemById()`, `filterItems()` (name-substring + AND-tag-filter search, used identically by `library.js` and `picker.js`), `MP_SUBTYPE_GROUPS`/`getDishGroup()` (a derived, not stored, coarse grouping — protein/vegetable/soup/carb — used by the weekly rule engine so items don't need a redundant group field alongside `subType`), and `getItemImagePath()`/`renderItemThumb(container, item)` (see "Item images" below). Item data ships as a JS file (not `.json` + `fetch()`) specifically so pages keep working when opened via `file://` — `fetch()` of a local JSON file is blocked by Chrome's CORS policy without a dev server, which would break the "just double-click index.html" workflow.
- **`js/storage.js`** — all `localStorage` reads/writes: `loadPlan()`/`savePlan()`/`clearPlan()` for the one current plan (key `menuPlanner.currentPlan`), `loadLastChoice()`/`saveLastChoice()` for remembered scope/mode defaults (key `menuPlanner.lastChoice`). `loadPlan()` returns `null` on missing/corrupt/version-mismatched data rather than throwing — callers must handle a `null` plan (a plan saved under an older `MP_PLAN_VERSION` simply fails to load rather than being migrated).
- **`js/generator.js`** — `getSlotsForScope(scope)` returns the ordered list of `{key, label}` slot descriptors for `"meal"` (1 slot) and `"day"` (2 slots), both using the generic `"day{N}-{meal}"` key scheme; `"week"` is a deliberate exception (10 slots, weekday-named keys `mon-lunch`...`fri-dinner`, since week now has real Mon-Fri calendar identity — see `MP_WEEKDAY_KEYS`/`getWeekdayRows()`). `getDayGroupsForScope(scope)` is the single definition of "what counts as one calendar day" per scope (used by the rice-based-per-day rule; returns `[]` for `"meal"` scope, which has no day context). `generatePlanSlots()` filters candidates by include/exclude tags, then fills each slot applying the weekly planning rules above as best-effort heuristics — day-specific rules (meatless Monday, fixed Tuesday dinner, Wednesday's fixed structure) hook off literal slot-key equality and only fire for `scope === "week"`; the rest (one-dish+vegetable pairing, seafood soft-weighting, quick-lunch soft-weighting, carb-or-one-dish, no-duplicate-subtype, rice-based-per-day) apply universally. The quick-lunch rule works the same way as the Monday-vegetarian pool restriction just above it in the code — before filling a lunch slot, with probability `MP_QUICK_LUNCH_PROBABILITY` the candidate pool is narrowed to `quick`-tagged items (falling back to the unfiltered pool if that leaves nothing). Dish-level repeats are avoided within a sliding window (sized `min(candidates.length - 1, 4)`, self-shrinking for small filtered pools, falling back to allowing a repeat rather than failing when the pool is too small). There is no separate violation-tracking pass — a rule that can't be satisfied (e.g. no vegetable candidate left in the filtered pool) is simply left unsatisfied for that slot rather than recorded anywhere. Scope-shape logic lives entirely in `getSlotsForScope`/`getDayGroupsForScope` — see the one narrow exception noted under `planner.js` below.
- **`js/picker.js`** — the one shared "add a dish to a slot" modal (`openPicker({slotKey, existingIds, onSelect, onClearAll})`), lazily injected into the page on first use. Adds one dish per invocation (click a row → `onSelect(id)` → close) — call it again to add another dish to the same slot. It's the single code path for both manual-mode slot filling and overriding an autogenerated slot — there is no separate manual-mode assignment logic anywhere. Reuses `filterItems()` from `data.js` for its search/tag UI, matching `library.js`'s filtering behavior.
- **`js/planner.js`** (planner.html) — `initPlan()` either builds a fresh plan from a `sessionStorage` handoff (`menuPlanner.pendingChoice`, written by `index.js` and consumed/cleared here) or resumes the saved plan via `loadPlan()`; redirects to `index.html` if neither is available. `renderPlannerGrid()` is a full re-render of every slot cell on any change (same "just repaint everything" simplicity as the sudoku project); it branches on `scope === "week"` to render a Mon-Fri × Lunch/Dinner `<table>` (`buildWeekTable()`) instead of the flat card grid used by meal/day scope — **this is the one deliberate exception** to "nothing branches on scope," necessary because week is genuinely a 2D (weekday × mealtype) structure now. Both layouts build their cells with the same `buildSlotCell(slotDef, { showLabel })` — the week table passes `showLabel: false` since the row/column headers already convey which day/mealtime a cell is, while the flat meal/day grid needs the label since it has no such headers. `addDishToSlot()`/`removeDishFromSlot()` mutate the in-memory plan's slot array, save, and re-render. `buildPlanExportHtml()`/`exportPlanToWord()` build a separate, self-contained, image-free HTML rendering of the plan (not a reuse of the live interactive DOM) and trigger a `.doc` download via a `Blob` with `type: "application/msword"` — Word natively opens HTML saved with that MIME type/extension, so this needs no external library, consistent with the project's dependency-free convention. "Print Menu" just calls `window.print()`; the print-only styling that hides nav/buttons lives in `css/style.css`'s `@media print` block.
- **`js/library.js`** (library.html) — search box + tag chips over `filterItems()`, rendered as a grid grouped into fixed browsing categories (`MP_LIBRARY_CATEGORIES`: One-Dish Meals, Soups, Poultry, Other Meat (Beef/Pork), Seafood, Vegetarian (or almost), Others), each category rendered as a native `<details>`/`<summary>` (open by default) so the user can collapse/expand a category with no JS-driven toggle logic needed, plus a read-only detail modal (own `#mp-detail-overlay`, separate from `picker.js`'s `#mp-picker-overlay` since the two pages never both load) showing full tags/image/recipe, with a graceful "no recipe" fallback and the same convention-based image lookup as everywhere else (falls back to a placeholder if `images/<id>.png` doesn't load). `getLibraryCategory(item)` assigns every item to exactly one category by priority (first match wins: one-dish → soup → poultry → other-meat → seafood-tagged → vegetable/tofu/egg-or-vegetarian-tagged → others) — this is a library-only browsing concept, deliberately separate from `getDishGroup()`/`MP_SUBTYPE_GROUPS` in `data.js` (which serves the rule engine and only has protein/vegetable/soup/carb/other). The "Vegetarian (or almost)" bucket intentionally also catches vegetable/tofu/egg dishes that aren't strictly meat-free (e.g. built on chicken stock or oyster sauce), matching how the household actually treats those dishes, rather than only trusting the literal `vegetarian`/`vegan` tags.
- **`js/index.js`** (index.html) — scope/mode radio pickers, a 3-state tag chip cycle (neutral → include → exclude → neutral) for autogenerate filters, a "Resume last plan" banner when a saved plan exists, and the "Start" handler that validates (for autogenerate, checks `getGeneratorCandidates()` isn't empty before allowing navigation) and writes the `sessionStorage` handoff read by `planner.js`.
- **`js/admin.js`** (admin.html) — a local-only menu-authoring tool. **Deliberately not linked from `index.html`/`planner.html`/`library.html`'s nav** — see "Why `admin.html` is safe to leave unlinked but not wired to write anywhere" below. Loads `MP_ITEMS`/`MP_SUBTYPE_GROUPS` as its seed, then works entirely against an in-memory working copy that's autosaved to `localStorage` (key `menuPlanner.adminDraft`, `{items, groups}`) on every add/edit/delete — same "always persist immediately, no explicit save button" pattern as the rest of the app. `openItemForm(id)`/`handleFormSubmit()` are the one shared add-and-edit code path (`id === null` means creating). Tags are click-to-toggle chips (`populateFormTagChips()`, tracked in `mpAdminFormSelectedTags`), not a text field, matching the include/exclude chip UX used elsewhere in the app; a small "Add Tag" control (`handleAddNewTag()`) lets you introduce a brand-new tag not yet used by any item (held in `mpAdminExtraTagVocab` until the item is actually saved with it). The item list itself has search (by name), dish-type/food-group dropdowns, and the same tag-chip filtering (`renderAdminFilterTags()`) — reusing `filterItems()` from `data.js` for the name/tag part, same as `library.js`/`picker.js`. There's nothing image-related in the form at all — images aren't a stored field anymore (see "Item images" below), so there's nothing here to edit. `downloadGeneratedDataJs()` is the only thing that matters for the live site: it serializes the working copy into a complete, ready-to-drop-in replacement for `js/data.js` (using `JSON.stringify` for the data literals — quoted-key JSON is valid JS object/array syntax, so no hand-rolled serializer is needed) and triggers a download; the user is expected to copy it over `js/data.js` and commit/deploy themselves.

## Data model

- **Menu item** (`js/data.js`): `{ id, name, tags: string[], dishType: "one-dish" | "component", subType: string, isRiceBased: boolean, isCarbohydrate: boolean, recipe?: { ingredients?: string[], steps?: string[] } }`. `id` must stay unique — nothing validates this, so check by hand when adding items. No dedicated "meal type" field: lunch/dinner suitability, if wanted, is just another tag (e.g. `lunch-friendly`) — one filtering mechanism (tags) covers everything. `dishType` distinguishes a dish that's a full meal on its own ("one-dish") from one meant to be combined with others ("component"). `subType` is the fine-grained identity the no-duplicate-per-meal rule dedupes on (e.g. `"chicken"`, `"vegetable-kangkong"`, `"soup-pork-rib"`, `"rice-plain"`); coarser groupings (protein/vegetable/soup/carb) are derived from it via `getDishGroup()` in `data.js`, not stored per item. There is deliberately no `image` field — see "Item images" below.
- **Saved plan** (`localStorage['menuPlanner.currentPlan']`, `MP_PLAN_VERSION` 2): `{ version, scope, mode, createdAt, slots }` where `slots` is keyed `"day{N}-{meal}"` for `"meal"`/`"day"` scope, or weekday-named (`"mon-lunch"`...`"fri-dinner"`) for `"week"` scope (see `getSlotsForScope` above), and every value is a **`string[]` of dish ids** (never `null` — an empty slot is `[]`), since a meal can now hold more than one dish. Only one plan is ever kept — starting a new one from `index.html` overwrites it.

### Item images

Images are resolved purely by filename convention — **`images/<id>.png`** — there is no `image` field on the item object anywhere. To give a dish a picture, save a PNG named after its exact `id` (e.g. `images/fried-shishamo.png` for `fried-shishamo`) into `/images`; nothing else needs to change. `getItemImagePath(item)` in `js/data.js` builds that path, and `renderItemThumb(container, item)` renders an `<img>` into `container` with an `onerror` handler that swaps in a 🍽️ placeholder if the file 404s — this is how "look up the image, or assume it doesn't exist" is implemented, and it's used identically by `planner.js` (slot dish rows), `picker.js` (result rows), `library.js` (grid cards and the detail modal), and `admin.js` (list cards). Two things that trip people up: **only `.png` is checked** (no fallback to `.jpg`/`.webp`/etc.), and GitHub Pages serving is **case-sensitive**, so the filename must match the id's exact case (ids are always lowercase/hyphenated).

## Conventions to preserve

- Keep it dependency-free static files — no bundler, no framework, no `fetch()` of local data files.
- New menu items go directly into `MP_ITEMS` in `js/data.js`, including the `dishType`/`subType`/`isRiceBased`/`isCarbohydrate` fields; to give one a picture, just save `images/<id>.png` — don't add an `image` field, there isn't one (see "Item images" above).
- Any new "add a dish to a slot" interaction should go through `picker.js`'s existing `openPicker()`, not a new bespoke picker — that's what keeps manual mode and autogenerate-override from diverging. It's called once per dish added, not once per slot.
- If scope options ever change (e.g. adding a new planning scope), start from `getSlotsForScope()`/`getDayGroupsForScope()` in `generator.js` — the rest of the app is written to iterate whatever they return rather than assuming meal/day/week. The one exception is `planner.js`'s `renderPlannerGrid()`, which branches on `scope === "week"` to pick a table vs. flat-grid outer layout (see above) — keep that the *only* scope branch outside `generator.js` if the rendering ever needs to change further.
- If the weekly planning rules ever change, they live in one place: `generatePlanSlots()` in `generator.js`.
- **Why `admin.html` is safe to leave unlinked but not wired to write anywhere**: this is a static site with no backend, so nothing served from it can ever write back to the deployed `js/data.js` — the only way "the menu everyone sees" changes is a human editing the file and redeploying. That means `admin.html` cannot be a real security exposure no matter who finds its URL: at worst a visitor generates a `data.js` download for themselves, which affects nothing. Don't be tempted to "fix" this by adding real persistence (e.g. embedding a GitHub API token to auto-commit) — a secret embedded in client-side JS on a public site is readable by anyone and would be a genuine vulnerability, unlike the current design.
