# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, dependency-free menu-planning webapp: plan a single meal, a full day (lunch + dinner), or a full week (7 × lunch/dinner), either autogenerated from tag filters or built by hand, picking from a searchable, tagged library of menu items with optional images/recipes. No build step, no backend — `MP_ITEMS` in `js/data.js` is the entire "database," and the only persistence is `localStorage`. Deployable to GitHub Pages by committing static files as-is.

## Running / testing

No build or test tooling. Open `index.html`, `planner.html`, or `library.html` directly in a browser to try changes; reload to pick them up. There is no `fetch()` of any data file (see below), so opening files directly via `file://` works with no local server needed.

## Architecture

Three pages, each with its own small controller script, sharing common utility scripts loaded before it. All scripts are plain (non-module) `<script src>` includes defining top-level functions/consts as globals — no bundler, no import/export.

- **`js/data.js`** — the menu item master list (`MP_ITEMS`, hand-edited directly — no in-app admin UI) plus shared helpers `getAllTags()`, `getItemById()`, `filterItems()` (name-substring + AND-tag-filter search, used identically by `library.js` and `picker.js`). Item data ships as a JS file (not `.json` + `fetch()`) specifically so pages keep working when opened via `file://` — `fetch()` of a local JSON file is blocked by Chrome's CORS policy without a dev server, which would break the "just double-click index.html" workflow.
- **`js/storage.js`** — all `localStorage` reads/writes: `loadPlan()`/`savePlan()`/`clearPlan()` for the one current plan (key `menuPlanner.currentPlan`), `loadLastChoice()`/`saveLastChoice()` for remembered scope/mode defaults (key `menuPlanner.lastChoice`). `loadPlan()` returns `null` on missing/corrupt/version-mismatched data rather than throwing — callers must handle a `null` plan.
- **`js/generator.js`** — `getSlotsForScope(scope)` is the key abstraction that makes one unified planner UI work for all three scopes: it returns the ordered list of `{key, label}` slot descriptors for `"meal"` (1 slot), `"day"` (2 slots), or `"week"` (14 slots), all using the same `"day{N}-{meal}"` key scheme. `generatePlanSlots()` filters candidates by include/exclude tags, then walks the slot list assigning random picks while avoiding repeats within a sliding window (sized `min(candidates.length - 1, 4)`, self-shrinking for small filtered pools, falling back to allowing a repeat rather than failing when the pool is too small). Nothing here branches on scope beyond how many slot keys come back — changing scope logic means changing `getSlotsForScope`, not the generator.
- **`js/picker.js`** — the one shared "assign an item to a slot" modal (`openPicker({slotKey, currentItemId, onSelect})`), lazily injected into the page on first use. It's the single code path for both manual-mode slot filling and overriding an autogenerated slot — there is no separate manual-mode assignment logic anywhere. Reuses `filterItems()` from `data.js` for its search/tag UI, matching `library.js`'s filtering behavior.
- **`js/planner.js`** (planner.html) — `initPlan()` either builds a fresh plan from a `sessionStorage` handoff (`menuPlanner.pendingChoice`, written by `index.js` and consumed/cleared here) or resumes the saved plan via `loadPlan()`; redirects to `index.html` if neither is available. `renderPlannerGrid()` is a full re-render of every slot card on any change (same "just repaint everything" simplicity as the sudoku project) — `assignSlot()` mutates the in-memory plan, saves, and re-renders.
- **`js/library.js`** (library.html) — search box + tag chips over `filterItems()`, plus a read-only detail modal (own `#mp-detail-overlay`, separate from `picker.js`'s `#mp-picker-overlay` since the two pages never both load) showing full tags/image/recipe with graceful "no image"/"no recipe" fallbacks.
- **`js/index.js`** (index.html) — scope/mode radio pickers, a 3-state tag chip cycle (neutral → include → exclude → neutral) for autogenerate filters, a "Resume last plan" banner when a saved plan exists, and the "Start" handler that validates (for autogenerate, checks `getGeneratorCandidates()` isn't empty before allowing navigation) and writes the `sessionStorage` handoff read by `planner.js`.

## Data model

- **Menu item** (`js/data.js`): `{ id, name, tags: string[], image?: string, recipe?: { ingredients?: string[], steps?: string[] } }`. `id` must stay unique — nothing validates this, so check by hand when adding items. No dedicated "meal type" field: lunch/dinner suitability, if wanted, is just another tag (e.g. `lunch-friendly`) — one filtering mechanism (tags) covers everything.
- **Saved plan** (`localStorage['menuPlanner.currentPlan']`): `{ version, scope, mode, createdAt, slots }` where `slots` is always keyed `"day{N}-{meal}"` regardless of scope (see `getSlotsForScope` above) and values are an item `id` or `null`. Only one plan is ever kept — starting a new one from `index.html` overwrites it.

## Conventions to preserve

- Keep it dependency-free static files — no bundler, no framework, no `fetch()` of local data files.
- New menu items go directly into `MP_ITEMS` in `js/data.js`; new images go in `/images` and get referenced by relative path.
- Any new "assign item to a slot" interaction should go through `picker.js`'s existing `openPicker()`, not a new bespoke picker — that's what keeps manual mode and autogenerate-override from diverging.
- If scope options ever change (e.g. adding a new planning scope), start from `getSlotsForScope()` in `generator.js` — the rest of the app (`planner.js`, the grid rendering) is written to iterate whatever it returns rather than assuming meal/day/week.
