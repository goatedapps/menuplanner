# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, dependency-free menu-planning webapp. Vocabulary: the **Menu** is the full list of available **Dishes** (`MP_ITEMS`); a **Meal** is Lunch or Dinner, comprising one or more Dishes. You can plan a single meal, a full day (lunch + dinner), or a full work week (Mon-Fri × lunch/dinner), either autogenerated from tag filters and a set of planning rules (see below) or built by hand, picking dishes from a searchable, tagged library with optional images/recipes. No build step, no backend — `MP_ITEMS` in `js/data.js` is the entire "database," and the only persistence is `localStorage`. Deployable to GitHub Pages by committing static files as-is.

### Weekly planning rules

Week-scope autogeneration applies these rules as **best-effort heuristics** — it leans toward satisfying them but never retries/backtracks/fails generation, and there is no in-app warning UI for unsatisfied rules; the user reviews the generated plan and hand-fixes anything off via the picker:

- Monday dinner is restricted to `meatless`-tagged items ("meatless Monday").
- Every day has at least one rice-based **meal** — not just any rice-based dish anywhere in the day. A meal qualifies if it's a one-dish rice/porridge meal (e.g. fried rice, chicken porridge), or a plain rice/porridge component dish combined with at least one vegetable and one protein in that same meal.
- A one-dish-meal dish, once picked for a meal, is paired with exactly one vegetable dish and nothing else.
- Wednesday dinner has a fixed structure: plain rice + a vegetable + a meat-or-fish dish + a soup + one more (any) dish.
- Seafood is a soft dinner preference, not a hard lunch ban.
- Tuesday dinner is hardcoded to "Yong Tau Foo Bee Tai Mak".
- Every meal has either a one-dish meal, or at least one carbohydrate dish among its components.
- No two dishes of the same sub-type (`item.subType`) appear in one meal.
- Lunch is a "quick" meal (tagged `quick`) about 80% of the time — a soft, per-slot probability (`MP_QUICK_LUNCH_PROBABILITY`), not a hard filter.
- Once a meal has a plain rice/porridge base (a `component` dish with `subType` `rice-plain`/`porridge`), the rest of that meal prefers `match-with-rice`-tagged dishes. Once a one-dish meal tagged `noodles` is picked, its paired vegetable (see the one-dish+vegetable rule above) prefers to also be `match-with-noodles`-tagged. Both are soft — the base/anchor itself is unconstrained, and every place this narrows a candidate pool falls back to the unnarrowed pool rather than picking nothing.

## Running / testing

No build or test tooling. Open `index.html`, `planner.html`, or `library.html` directly in a browser to try changes; reload to pick them up. There is no `fetch()` of any data file (see below), so opening files directly via `file://` works with no local server needed.

## Architecture

Three pages, each with its own small controller script, sharing common utility scripts loaded before it. All scripts are plain (non-module) `<script src>` includes defining top-level functions/consts as globals — no bundler, no import/export.

- **`js/data.js`** — the menu item master list (`MP_ITEMS`, normally hand-edited directly, or regenerated via `admin.html` — see below) plus shared helpers `getAllTags()`, `getItemById()`, `filterItems()` (name-substring + AND-tag-filter search, with an optional `excludeTags` for a NOT-tag filter — `library.js`/`picker.js` only ever pass `tagFilters`, `admin.js` is the one caller that also passes `excludeTags`, via its 3-state include/exclude/neutral chip cycle), `MP_SUBTYPE_GROUPS`/`getDishGroup()` (a derived, not stored, coarse grouping — protein/vegetable/soup/carb — used by the weekly rule engine so items don't need a redundant group field alongside `subType`), `MP_LIBRARY_CATEGORIES`/`getLibraryCategory()`/`groupByLibraryCategory()` (a *separate*, broader browsing categorization — One-Dish Meals, Soups, Poultry, Other Meat (Beef/Pork), Seafood, Vegetarian (or almost), Others — shared by `library.js`'s grid and `picker.js`'s "add a dish" modal so both group results identically; every item lands in exactly one category by priority, first match wins: one-dish → soup → poultry → other-meat → seafood-tagged → vegetable/tofu/egg-or-`meatless`-tagged → others; "Vegetarian (or almost)" deliberately also catches vegetable/tofu/egg dishes that aren't strictly meat-free, e.g. built on chicken stock or oyster sauce, matching how the household actually treats those dishes — this tag check must stay in sync with whatever tag actually means "no meat" on items (it silently checked the retired `vegetarian`/`vegan` tags for a while after they were renamed to `meatless`, which miscategorized several items into "Others"; the same class of bug hit `generator.js`'s meatless-Monday check too — see `isMeatlessItem()` there)), and `getItemImagePath()`/`renderItemThumb(container, item)` (see "Item images" below). Item data ships as a JS file (not `.json` + `fetch()`) specifically so pages keep working when opened via `file://` — `fetch()` of a local JSON file is blocked by Chrome's CORS policy without a dev server, which would break the "just double-click index.html" workflow.
- **`js/storage.js`** — all `localStorage` reads/writes: `loadPlan()`/`savePlan()`/`clearPlan()` for the one current plan (key `menuPlanner.currentPlan`), `loadLastChoice()`/`saveLastChoice()` for remembered scope/mode defaults (key `menuPlanner.lastChoice`). `loadPlan()` returns `null` on missing/corrupt/version-mismatched data rather than throwing — callers must handle a `null` plan (a plan saved under an older `MP_PLAN_VERSION` simply fails to load rather than being migrated). Separately, `loadSavedPlans()`/`saveSavedPlansList()`/`addSavedPlan(name, plan)`/`removeSavedPlan(id)` manage a distinct, user-curated "Saved Menu Plans" list (key `menuPlanner.savedPlans`, capped at `MP_MAX_SAVED_PLANS` = 10) — a named snapshot the user explicitly keeps via `planner.js`'s "Save Meal" button, independent of the single auto-saved current plan. `addSavedPlan()` returns `{ok:true, entry}` or `{ok:false, reason}`; at the cap it **rejects rather than evicting** the oldest entry, matching the app's non-destructive conventions elsewhere — the user has to free a slot themselves. `loadSavedPlans()` returns `[]` on missing/corrupt data, same graceful convention as `loadPlan()`.
- **`js/generator.js`** — `getSlotsForScope(scope)` returns the ordered list of `{key, label}` slot descriptors for `"meal"` (1 slot) and `"day"` (2 slots), both using the generic `"day{N}-{meal}"` key scheme; `"week"` is a deliberate exception (10 slots, weekday-named keys `mon-lunch`...`fri-dinner`, since week now has real Mon-Fri calendar identity — see `MP_WEEKDAY_KEYS`/`getWeekdayRows()`). `getDayGroupsForScope(scope)` is the single definition of "what counts as one calendar day" per scope (used by the rice-based-meal-per-day rule; returns `[]` for `"meal"` scope, which has no day context). `generatePlanSlots()` filters candidates by include/exclude tags, then fills each slot applying the weekly planning rules above as best-effort heuristics — day-specific rules (meatless Monday, fixed Tuesday dinner, Wednesday's fixed structure) hook off literal slot-key equality and only fire for `scope === "week"`; the rest (one-dish+vegetable pairing, seafood soft-weighting, quick-lunch soft-weighting, carb-or-one-dish, no-duplicate-subtype, rice-based-meal-per-day) apply universally. The per-slot fill logic (day-specific fixed rules, meatless-Monday/quick-lunch pool restriction, `fillNormalMeal()`) lives in `generateSlotDishIds(items, scope, slotKey, candidates, recentWindow, windowSize)`, factored out so `regenerateSlot(items, scope, slotKey, includeTags, excludeTags)` can reuse it for planner.js's per-slot "Regenerate" button — a single-slot regen builds its own fresh candidate pool and an *empty* recency window (no memory of other slots, unlike a full `generatePlanSlots()` pass), so it's a true "redo just this one meal," not aware of what's elsewhere in the plan. The quick-lunch rule works the same way as the Monday-meatless pool restriction just above it in the code (`isMeatlessItem(item)` checks the `meatless` tag) — before filling a lunch slot, with probability `MP_QUICK_LUNCH_PROBABILITY` the candidate pool is narrowed to `quick`-tagged items (falling back to the unfiltered pool if that leaves nothing). The rice-based-meal rule is checked via `isRiceBasedMeal(dishIds, items)`/`hasPlainRiceOrPorridgeBase(dishes)` — a *meal* qualifies (one-dish rice/porridge, or a plain rice/porridge component dish plus a vegetable plus a protein together), not just "any `isRiceBased` dish exists somewhere in the day"; the day-group backfill tries to add whichever of those three pieces a swappable meal is missing, with no guarantee all three end up findable. `preferTaggedPool(pool, tag)` is the shared shape behind every soft tag preference in the file (narrow to `tag`, fall back to the unfiltered pool if that's empty) — including the match-with-rice/match-with-noodles pairing: `fillNormalMeal()`'s component-drawing loop checks `hasPlainRiceOrPorridgeBase(dishes)` before each subsequent pick and narrows to `match-with-rice` once true, `buildWednesdayDinner()`'s `takeFromGroup()` does the same after its always-first rice-plain pick, and rule b's day-group backfill (`tryAdd()`) does it for the vegetable/protein it adds; the noodles side is simpler since every `noodles`-tagged item is `dishType: "one-dish"` in practice, so it's just a one-line narrowing of the rule-c vegetable pairing in `fillNormalMeal()`. Both are pick-time-only — a rice-plain/porridge dish picked *after* other components already got chosen (e.g. via the rule-g carb backfill at the very end) doesn't retroactively realign anything already picked, consistent with the file's no-backtracking design. Dish-level repeats are avoided within a sliding window (sized `min(candidates.length - 1, 4)`, self-shrinking for small filtered pools, falling back to allowing a repeat rather than failing when the pool is too small). There is no separate violation-tracking pass — a rule that can't be satisfied (e.g. no vegetable candidate left in the filtered pool) is simply left unsatisfied for that slot rather than recorded anywhere. Scope-shape logic lives entirely in `getSlotsForScope`/`getDayGroupsForScope` — see the one narrow exception noted under `planner.js` below.
- **`js/picker.js`** — the one shared "add a dish to a slot" modal (`openPicker({slotKey, existingIds, onSelect, onQuickAdd})`), lazily injected into the page on first use. Adds one dish per invocation (click a row's main area → `onSelect(id)` → close) — call it again to add another dish to the same slot. It's the single code path for both manual-mode slot filling and overriding an autogenerated slot — there is no separate manual-mode assignment logic anywhere. Reuses `filterItems()` from `data.js` for its search/tag UI, matching `library.js`'s filtering behavior. Results are grouped into the same `MP_LIBRARY_CATEGORIES` buckets as `library.js` (via `groupByLibraryCategory()` in `data.js`), rendered as collapsible `<details>` sections — all collapsed when the picker first opens. Each category's open/closed state lives in `mpPickerState.openCategories` (keyed by category key) and is only changed by the user actually toggling that category (a `toggle` event listener writes it back); typing a search or clicking a tag filter re-renders the whole result list but reads from that same stored state, so it does **not** force-expand or force-collapse anything — a deliberate fix after an earlier version auto-expanded every category on any search/filter change, which the user found surprising. Each row is a `<div class="mp-picker-row">` wrapping two sibling `<button>`s (a button can't nest inside another button): `.mp-picker-row-main` (thumb+name+tags, click → add) and a small `.mp-picker-row-info` ("i") button that opens the same detail view as `library.js` via `openItemDetail(item, { onAdd })` (see `js/detail.js`) — letting the user check tags/image/recipe before committing, with an "Add to this meal" button inside that detail view as a shortcut back into the same add flow. Below the results list, a separate `.mp-picker-quickadd` row (a plain text input + "Add" button, submit on click or Enter) lets the user type a dish name that isn't in the library at all — `submitPickerQuickAdd()` trims it, no-ops silently if blank, and otherwise calls `onQuickAdd(name)` then closes, same as a normal pick; the picker itself has no idea what happens to that name, it's purely `planner.js`'s `addCustomDishToSlot()` that turns it into a plan-scoped dish (see `customDishes` in the data model below) — deliberately kept out of `MP_ITEMS`/the real database, since quick-add is explicitly a "just the name, nothing else" shortcut. Otherwise deliberately does nothing else — clearing a whole slot lives on the slot card itself in `planner.js` (`.mp-slot-clear-btn`, shown only when the slot has dishes), not bundled into the picker; it used to be a "Clear all dishes" button inside this modal, which read as ambiguous (unclear it cleared the whole meal, not just the picker) and blurred the picker's single-purpose "add one dish" job.
- **`js/detail.js`** — the shared read-only item detail modal (own `#mp-detail-overlay`, separate from `picker.js`'s `#mp-picker-overlay` so the two can be open at once), used by both `library.js` (plain browsing, `openItemDetail(item)`) and `picker.js` (`openItemDetail(item, { onAdd })`, which adds an "Add to this meal" button to the same modal). Its own Escape-key handler only acts `if (!overlay.hidden)`, and `picker.js`'s Escape handler checks whether the detail overlay is visible before closing itself — together these mean pressing Escape closes only the top-most modal (detail first, then picker) rather than both at once.
- **`js/planner.js`** (planner.html) — `initPlan()` either builds a fresh plan from a `sessionStorage` handoff (`menuPlanner.pendingChoice`, written by `index.js` and consumed/cleared here) or resumes the saved plan via `loadPlan()`; redirects to `index.html` if neither is available. The handoff's `mode` is `"autogenerate"` (calls `generatePlanSlots()`), `"manual"` (leaves every slot empty), or `"fortune"` (written by `js/fortune.js`'s wheel — assigns `plan.slots["day1-lunch"] = pending.dishIds` directly, no generation call, since the meal was already chosen by the spin; scope is always `"meal"` for a fortune result, which always uses that one slot key). `renderPlannerGrid()` is a full re-render of every slot cell on any change (same "just repaint everything" simplicity as the sudoku project); it branches on `scope === "week"` to render a Mon-Fri × Lunch/Dinner `<table>` (`buildWeekTable()`) instead of the flat card grid used by meal/day scope — **this is the one deliberate exception** to "nothing branches on scope," necessary because week is genuinely a 2D (weekday × mealtype) structure now. Both layouts build their cells with the same `buildSlotCell(slotDef, { showLabel })` — the week table passes `showLabel: false` since the row/column headers already convey which day/mealtime a cell is, while the flat meal/day grid needs the label since it has no such headers. Within a meal, dishes display carbohydrate-first (`sortDishesCarbFirst()`, a stable sort by `item.isCarbohydrate`) — purely cosmetic, applied at render time only (in `buildSlotCell` and `dishNamesHtml`, so screen/print/Word export all agree), never reordering the underlying `plan.slots[key]` array itself, since nothing else (add/remove, `existingIds` checks) depends on that array's order. `addDishToSlot()`/`removeDishFromSlot()` mutate the in-memory plan's slot array, save, and re-render (`removeDishFromSlot()`/`clearSlotArray()` also drop any notes for the dish(es) removed, so notes never outlive the dish they're attached to). `getPlanDishItem(id)` is the one place a slot's dish id gets resolved to an actual item — `getItemById(MP_ITEMS, id)` first, falling back to `mpCurrentPlan.customDishes[id]` — used everywhere `buildSlotCell()`/`dishNamesHtml()` used to call `getItemById(MP_ITEMS, id)` directly, so both real items and picker-quick-added ones render identically. `addCustomDishToSlot(slotKey, name)` (wired as the picker's `onQuickAdd`) is the other end of that: generates an id, stores a minimal `{id, name, tags: [], custom: true}` record in `plan.customDishes` — deliberately *not* `MP_ITEMS`, since quick-add is explicitly name-only with no tags/dishType/recipe — then calls `addDishToSlot()` same as any normal pick. `pruneUnusedCustomDishes()` sweeps `plan.customDishes` for entries no longer referenced by any slot and deletes them; called from `removeDishFromSlot()`, `clearSlotArray()`, and `regenerateMealSlot()` (every path that can drop a dish out of a slot) so a removed quick-add doesn't linger in storage forever. `regenerateMealSlot(slotKey)` (wired to each card's "↻ Regenerate" button, next to "+ Add dish") re-runs `regenerateSlot()` from `generator.js` against the plan's stored `includeTags`/`excludeTags` and replaces that slot's dishes outright — day-specific fixed rules (Tuesday dinner, Wednesday dinner, meatless Monday) still apply since they're keyed off scope+slotKey; per-dish notes for the replaced dishes are dropped (they were about specific dishes that are now gone) but the whole-meal note is untouched. `moveDishToSlot(fromSlotKey, toSlotKey, dishId)` backs drag-and-drop between slots (e.g. dragging a dish from Tue lunch onto the Wed lunch card) — each dish's wrapper (`buildSlotDishRow()`'s `.mp-slot-dish-block`) is `draggable`, carrying `{slotKey, dishId}` as JSON via the native HTML5 `dataTransfer` API (no library — desktop mouse-drag only, this doesn't work via touch); each `.mp-slot-card` is the drop target (`dragover`/`drop` handlers set up in `buildSlotCell()`, with a `.mp-slot-drop-target` CSS class toggled for hover feedback). A move carries the dish's per-dish note along to its new slot (unlike a plain remove, which deletes it) since the dish itself hasn't left the plan, just relocated. Each dish row (`buildSlotDishRow()`) also wraps its thumb+name+tags in a `.mp-slot-dish-view` button that calls `openItemDetail(dish)` (from `js/detail.js`, shared with `library.js`/`picker.js`) to show the full detail modal — kept as a separate button from the drag-wrapper and the remove button, and the note input lives outside all of them (a button can't nest a form control). `.mp-slot-dish-view:hover` gets a `--paper` background (padding/negative-margin offset so the highlight doesn't shift the row's layout) as the only visual cue that a dish is clickable, since nothing else about it looks interactive. `getDishNote()`/`setDishNote()` read/write `plan.notes[slotKey][dishId]` directly and save on every keystroke *without* calling `renderPlannerGrid()` (a full repaint mid-typing would yank focus out of the field — this is the one place in the file that saves without re-rendering, along with `setMealNote()` below). `buildSlotCell()` also renders a separate `.mp-slot-meal-note-input` (right after the slot label, before the dish list) for a whole-meal note independent of any dish; `getMealNote()`/`setMealNote()` read/write `plan.mealNotes[slotKey]` the same way. `buildPlanExportHtml()`/`exportPlanToWord()` build a separate, self-contained, image-free HTML rendering of the plan (not a reuse of the live interactive DOM) and trigger a `.doc` download via a `Blob` with `type: "application/msword"` — Word natively opens HTML saved with that MIME type/extension, so this needs no external library, consistent with the project's dependency-free convention. The export has no title/heading in the document body (deliberately removed) and is black-on-white only (inline `style` attributes only — no color anywhere, since Word renders plain HTML/CSS but the doc should stay printable/photocopy-safe). `mealNoteHtml()` renders the whole-meal note (if any) above `dishNamesHtml()`'s output in each cell; `dishNamesHtml()` renders each meal's dishes as a `<ul>` bullet list, one `<li>` per dish with its per-dish note (if any) in italics — tags are deliberately never included in the export. `#mp-save-plan-btn` ("Save Meal", in the same `#mp-plan-actions` toolbar as Print/Export/Start Over) calls `handleSavePlanClick()`: `prompt()`s for a name (defaulting to `"{Scope label} - {today's date}"`), then `addSavedPlan(name, mpCurrentPlan)` — on `{ok:false}` (10-plan cap hit) shows the rejection reason via `alert()`, same native-dialog convention `admin.js` already uses for delete confirmations, deliberately not a new custom modal. "Print Menu" just calls `window.print()` against the live DOM (a different code path from the Word export, not sharing `dishNamesHtml()`/`mealNoteHtml()`); the print-only styling in `css/style.css`'s `@media print` block hides nav/buttons, `.mp-slot-tags`, *and* `.mp-slot-thumb` (dish photos — too small to be legible on paper), restyles each `.mp-slot-dish-block` (not the on-screen `.mp-slot-dish-row` grid — the block is the print-time bullet unit, since it also covers the note line beneath the row) into a plain bulleted line (a `::before { content: "•" }`, since it isn't inside a real `<ul>`), and strips both note inputs' editable chrome (hiding either entirely if empty) so print matches the Word export's "name + notes, no tags/images" content.
- **`js/library.js`** (library.html) — search box + tag chips over `filterItems()`, rendered as a grid grouped by `groupByLibraryCategory()` (see `data.js`) into fixed browsing categories, each category rendered as a native `<details>`/`<summary>` (open by default here — `picker.js` is the one that defaults to collapsed) so the user can collapse/expand a category with no JS-driven toggle logic needed. Clicking a card calls `openItemDetail(item)` from `js/detail.js` (shared with `picker.js`) to show full tags/image/recipe, with a graceful "no recipe" fallback and the same convention-based image lookup as everywhere else (falls back to a placeholder if `images/<id>.png` doesn't load).
- **`js/index.js`** (index.html) — scope/mode radio pickers, a 3-state tag chip cycle (neutral → include → exclude → neutral) for autogenerate filters, a "Resume last plan" banner when a saved plan exists, a collapsible "Saved Menu Plans" shelf (see below), and the "Start" handler that validates (for autogenerate, checks `getGeneratorCandidates()` isn't empty before allowing navigation) and writes the `sessionStorage` handoff read by `planner.js`. `renderSavedPlans()` builds `#mp-saved-plans-container`'s content from `loadSavedPlans()` (`js/storage.js`): a `<details class="mp-library-category">` (reusing `library.js`'s chalkboard-style collapsible class for visual consistency, but **defaulting collapsed**, unlike library's own categories, since this is a quick-access shelf rather than something meant to browse open) titled `"Saved Menu Plans (N)"`, omitted entirely when the list is empty. Each row is two buttons: clicking the plan's name/date loads it — version-gates against `MP_PLAN_VERSION` first (mirroring `loadPlan()`'s own protection), then `savePlan(entry.plan)` followed by a plain navigation to `planner.html` (no `sessionStorage` handoff needed, since `initPlan()` already falls back to `loadPlan()` when there's no pending choice) — and a small "×" button (`confirm()` guarded, matching `admin.js`'s delete-confirmation convention) calls `removeSavedPlan(entry.id)` and re-renders. "🎡 Meal of Fortune" (`value="fortune"`) is the *first* option in `#mp-scope-group` and is `checked` by default in the HTML — deliberately the page's default landing tab every time, not just on a first-ever visit, which is why `loadLastChoice()`'s restoration only ever re-checks the *mode* radio, never the scope radio. Fortune is a different flow entirely (no mode/Start button) — `updateScopeVisibility()` hides `#mp-mode-section` and `#mp-start-btn` and shows `#mp-fortune-section` when it's selected (hiding the *whole section*, not just its `#mp-mode-only` contents, is deliberate — leaving the emptied section visible left a blank card-styled box on screen). Tag filters (`#mp-autogen-options`) apply to both flows, so rather than duplicating that chip UI/state, `updateScopeVisibility()` **reparents the same DOM node** between the two layouts: it lives in `#mp-mode-section` normally, and gets moved to inside `#mp-fortune-section` (positioned via `insertBefore(autogenOptions, fortuneWarning)`, i.e. below the wheel — moved back via `modeSection.appendChild(autogenOptions)` for the other scopes) whenever fortune is selected. `initFortuneWheel()` (from `js/fortune.js`) is wired up with `getIncludeTags`/`getExcludeTags` accessor closures over the *same* `tagStates` object the normal chips use.
- **`js/fortune.js`** (index.html) — the "Meal of Fortune" wheel. `initFortuneWheel()` renders the wheel's visible segments **once**, immediately (so it never shows as a blank circle), via `renderFortuneWheelStatic()` — `MP_FORTUNE_SEGMENTS` (16) equal pie slices as one `conic-gradient()`, each labeled with a plain letter (`MP_FORTUNE_LETTERS`, "A".."P") via an absolutely-positioned `.mp-fortune-wedge-label` span rotated to that segment's mid-angle (`rotate(angle) translateY(-radius)` — `rotate(0)` points straight up via `translateY`, which conveniently already matches `conic-gradient()`'s own 0deg-at-top convention, so no extra angle offset is needed). These labels are deliberately generic and static, never rebuilt — with real dish names the wheel could only ever show a handful of candidates, and at 16 segments would be unreadable anyway. `#mp-fortune-spin-btn` (plain "Spin") sits as a fixed circular hub at `#mp-fortune-wheel-wrap`'s center — a sibling of the rotating `#mp-fortune-wheel` div, not a descendant, so it never spins itself, same as the pointer. `spinFortuneWheel()` picks the actual winning meal completely independently of the wheel's visuals: one `getGeneratorCandidates()` + `fillNormalMeal()` call (`generator.js`), same as any single autogenerated slot — not a pool of candidates to choose among, since nothing on the wheel needs to correspond to it. Separately, it picks a random *segment index* purely as an animation target, computes a landing rotation (several full turns + an offset so that segment ends at the fixed pointer), and animates `#mp-fortune-wheel`'s `transform: rotate()` with a CSS transition — reset to `rotate(0deg)` with `transition: none` (plus a forced reflow via `wheel.offsetHeight`) before every spin so rotations don't compound. On `transitionend`, `revealFortuneWinner()` renders the winning meal's dishes (reusing `renderItemThumb()`, the same `.mp-item-thumb`/`.mp-item-name`/`.mp-item-tags` classes as everywhere else) with a single action, "Use This Meal!", which writes the same `sessionStorage["menuPlanner.pendingChoice"]` handoff `index.js`'s Start button uses, but shaped `{ scope: "meal", mode: "fortune", dishIds, includeTags, excludeTags }` (the meal is already chosen, no generation needed on the other end — see `planner.js`'s `initPlan()`) and deliberately skips `saveLastChoice()`, since a spontaneous fortune pick shouldn't override the user's normal remembered scope/mode default. There's deliberately no separate "Spin Again" button — the wheel's own hub button already re-spins from scratch on click regardless of its current rotation, so a second control would be redundant. `#mp-fortune-section` has no heading of its own in `index.html` (the 🎡 emoji and scope label on its selector tab already identify it, so a repeated title inside the revealed section was redundant); the wheel itself is sized via CSS (`#mp-fortune-wheel-wrap { width: min(380px, 100%); aspect-ratio: 1/1; }` — `100%` rather than a viewport-relative unit, so it always respects `.mp-container`/`.mp-section`'s padding instead of overflowing on mobile) rather than a fixed pixel box, so `renderFortuneWheelStatic()` reads the wheel's actual rendered width (`wheel.offsetWidth`, a deliberate forced sync layout — fine since it's once per render, not per frame) and derives the wedge-label radius from it via `MP_FORTUNE_LABEL_RADIUS_RATIO` (145/190, preserving the original hand-tuned look at a ~190px radius) rather than a literal px constant, so labels stay inside the rim whether the wheel renders at 380px or smaller on a narrow phone.
- **`js/admin.js`** (admin.html) — a local-only menu-authoring tool. **Deliberately not linked from `index.html`/`planner.html`/`library.html`'s nav** — see "Why `admin.html` is safe to leave unlinked but not wired to write anywhere" below. Loads `MP_ITEMS`/`MP_SUBTYPE_GROUPS` as its seed, then works entirely against an in-memory working copy that's autosaved to `localStorage` (key `menuPlanner.adminDraft`, `{items, groups}`) on every add/edit/delete — same "always persist immediately, no explicit save button" pattern as the rest of the app. `openItemForm(id)`/`handleFormSubmit()` are the one shared add-and-edit code path (`id === null` means creating). Tags are click-to-toggle chips (`populateFormTagChips()`, tracked in `mpAdminFormSelectedTags`), not a text field, matching the include/exclude chip UX used elsewhere in the app; a small "Add Tag" control (`handleAddNewTag()`) lets you introduce a brand-new tag not yet used by any item (held in `mpAdminExtraTagVocab` until the item is actually saved with it). The item list itself has search (by name) plus the same categorized/collapsible rendering as `library.js` (`groupByLibraryCategory()`, see `data.js`) — no separate dish-type/food-group dropdowns anymore, those were removed in favor of the categories themselves. `renderAdminFilterTags()` is a 3-state include/exclude/neutral chip cycle (same convention as `index.js`'s autogenerate tag chips) so you can filter to "has tag X" or "does NOT have tag X"; both feed `mpAdminListFilters.tagFilters`/`.excludeTags` into `filterItems()` from `data.js`, same function `library.js`/`picker.js` use for the name/tag part (they just never pass `excludeTags`). There's nothing image-related in the form at all — images aren't a stored field anymore (see "Item images" below), so there's nothing here to edit. `downloadGeneratedDataJs()` is the only thing that matters for the live site: it serializes the working copy into a complete, ready-to-drop-in replacement for `js/data.js` (using `JSON.stringify` for the data literals — quoted-key JSON is valid JS object/array syntax, so no hand-rolled serializer is needed) and triggers a download; the user is expected to copy it over `js/data.js` and commit/deploy themselves. **Its function definitions (`getDishGroup`, `MP_LIBRARY_CATEGORIES`, `getLibraryCategory`, `groupByLibraryCategory`, `getAllTags`, `getItemById`, `filterItems`, `getItemImagePath`, `renderItemThumb`) are a hand-kept copy of `data.js`'s tail, not derived from it** — this has already caused one real bug (two functions and, later, three more went missing from the generated output for a while) and needs the same edit whenever `data.js`'s shared helpers change.

## Data model

- **Menu item** (`js/data.js`): `{ id, name, tags: string[], dishType: "one-dish" | "component", subType: string, isRiceBased: boolean, isCarbohydrate: boolean, recipe?: { ingredients?: string[], steps?: string[] } }`. `id` must stay unique — nothing validates this, so check by hand when adding items. No dedicated "meal type" field: lunch/dinner suitability, if wanted, is just another tag (e.g. `lunch-friendly`) — one filtering mechanism (tags) covers everything. `dishType` distinguishes a dish that's a full meal on its own ("one-dish") from one meant to be combined with others ("component"). `subType` is the fine-grained identity the no-duplicate-per-meal rule dedupes on (e.g. `"chicken"`, `"vegetable-kangkong"`, `"soup-pork-rib"`, `"rice-plain"`); coarser groupings (protein/vegetable/soup/carb) are derived from it via `getDishGroup()` in `data.js`, not stored per item. There is deliberately no `image` field — see "Item images" below.
- **Saved plan** (`localStorage['menuPlanner.currentPlan']`, `MP_PLAN_VERSION` 2): `{ version, scope, mode, createdAt, slots, notes, mealNotes, includeTags, excludeTags, customDishes }` where `slots` is keyed `"day{N}-{meal}"` for `"meal"`/`"day"` scope, or weekday-named (`"mon-lunch"`...`"fri-dinner"`) for `"week"` scope (see `getSlotsForScope` above), and every value is a **`string[]` of dish ids** (never `null` — an empty slot is `[]`), since a meal can now hold more than one dish. `notes` is `{ [slotKey]: { [dishId]: string } }` — a free-text note per dish-in-slot (e.g. "double portion", "use leftover rice"), entered inline in `planner.js`'s `buildSlotDishRow()` and read/written via `getDishNote()`/`setDishNote()`. `mealNotes` is `{ [slotKey]: string }` — a separate, single free-text note for the *whole meal* regardless of which dishes are in it (e.g. "Only ABC is eating"), entered via `.mp-slot-meal-note-input` in `buildSlotCell()` and read/written via `getMealNote()`/`setMealNote()`; deliberately not cleared when `clearSlotArray()`/`removeDishFromSlot()` remove dishes, since who's-eating-style context isn't tied to any particular dish. `includeTags`/`excludeTags` are the tag filters the plan was originally generated with (captured from `index.js`'s handoff in `initPlan()`, `[]` for manual-mode plans) — kept on the plan specifically so a per-slot "Regenerate" click later can reuse the same filters rather than regenerating against the unfiltered menu. `customDishes` is `{ [dishId]: { id, name, tags: [], custom: true } }` — plan-scoped "quick add" dishes typed into the picker's name-only row (see `picker.js`/`getPlanDishItem()` below), deliberately *not* pushed into `MP_ITEMS`, so a slot's dish ids can point at either a real item or one of these; pruned automatically (`pruneUnusedCustomDishes()`) whenever a dish drops out of every slot, so removed quick-adds don't linger in storage. All five of `notes`/`mealNotes`/`includeTags`/`excludeTags`/`customDishes` are additive and *not* covered by `MP_PLAN_VERSION` — a plan saved before any of them existed just loads with the empty default for whichever is missing (see the fallback in `planner.js`'s `DOMContentLoaded` handler) rather than failing to load, unlike an actual `slots` shape change. Only one *current* plan is ever kept — starting a new one from `index.html` overwrites it.
- **Saved Menu Plans list** (`localStorage['menuPlanner.savedPlans']`) — separate from the single current plan above: an array (max `MP_MAX_SAVED_PLANS` = 10) of `{ id, name, savedAt, plan }` entries, where `plan` is a full snapshot of a plan object in the exact shape described above (same `version`/`scope`/`mode`/`slots`/`notes`/etc.). Created via `planner.js`'s "Save Meal" button (`addSavedPlan(name, plan)` in `storage.js`) and browsed/loaded/deleted from a collapsible section on `index.html` (`renderSavedPlans()` in `index.js`) — see those files' bullets above for the full flow. `id` is a `${Date.now()}-${random}` string, unique enough for a personal, single-device list with no concurrent writers.

### Item images

Images are resolved purely by filename convention — **`images/<id>.png`** — there is no `image` field on the item object anywhere. To give a dish a picture, save a PNG named after its exact `id` (e.g. `images/fried-shishamo.png` for `fried-shishamo`) into `/images`; nothing else needs to change. `getItemImagePath(item)` in `js/data.js` builds that path, and `renderItemThumb(container, item)` renders an `<img>` into `container` with an `onerror` handler that swaps in a 🍽️ placeholder if the file 404s — this is how "look up the image, or assume it doesn't exist" is implemented, and it's used identically by `planner.js` (slot dish rows), `picker.js` (result rows), `library.js` (grid cards and the detail modal), and `admin.js` (list cards). Two things that trip people up: **only `.png` is checked** (no fallback to `.jpg`/`.webp`/etc.), and GitHub Pages serving is **case-sensitive**, so the filename must match the id's exact case (ids are always lowercase/hyphenated).

### Visual design

`css/style.css` implements an "enamel tray & kopitiam tile" identity, deliberately drawn from the app's real subject (Singaporean/Malaysian home cooking and hawker culture) rather than a generic palette — see the `:root` block for the full token list and rationale comment. Three font roles, system fonts only (no CDN, so the app keeps working fully offline via `file://`): `--font-stamp` (monospace — eyebrows, day labels, category headers, badges — an "order chit" feel), `--font-display` (Georgia — h1/h2/h3, dish names), `--font-body` (system sans — buttons, inputs, dense UI chrome). The one deliberate "bold" element is the rubber-stamp badge (`.mp-day-stamp`, injected by `getDayStamp()` in `planner.js`) shown **only** on the three week-scope slots whose meaning is already fixed by the planning rules above (`mon-dinner` = Meatless, `tue-dinner` = Fixed·YTF, `wed-dinner` = 3-Part) — it exists to encode real rule information, not as decoration, and isn't used anywhere else. Everything else (buttons, chips, forms, `admin.html`) shares the same tokens but stays visually quiet. Dish thumbnails render circular with a steel ring (`.mp-item-thumb`, `.mp-picker-row-thumb`, `.mp-slot-dish-row .mp-slot-thumb`) as a consistent "enamel plate" motif everywhere a dish photo appears.

## Conventions to preserve

- Keep it dependency-free static files — no bundler, no framework, no `fetch()` of local data files.
- New menu items go directly into `MP_ITEMS` in `js/data.js`, including the `dishType`/`subType`/`isRiceBased`/`isCarbohydrate` fields; to give one a picture, just save `images/<id>.png` — don't add an `image` field, there isn't one (see "Item images" above).
- Any new "add a dish to a slot" interaction should go through `picker.js`'s existing `openPicker()`, not a new bespoke picker — that's what keeps manual mode and autogenerate-override from diverging. It's called once per dish added, not once per slot.
- If scope options ever change (e.g. adding a new planning scope), start from `getSlotsForScope()`/`getDayGroupsForScope()` in `generator.js` — the rest of the app is written to iterate whatever they return rather than assuming meal/day/week. The one exception is `planner.js`'s `renderPlannerGrid()`, which branches on `scope === "week"` to pick a table vs. flat-grid outer layout (see above) — keep that the *only* scope branch outside `generator.js` if the rendering ever needs to change further.
- If the weekly planning rules ever change, they live in one place: `generatePlanSlots()` in `generator.js`.
- **Why `admin.html` is safe to leave unlinked but not wired to write anywhere**: this is a static site with no backend, so nothing served from it can ever write back to the deployed `js/data.js` — the only way "the menu everyone sees" changes is a human editing the file and redeploying. That means `admin.html` cannot be a real security exposure no matter who finds its URL: at worst a visitor generates a `data.js` download for themselves, which affects nothing. Don't be tempted to "fix" this by adding real persistence (e.g. embedding a GitHub API token to auto-commit) — a secret embedded in client-side JS on a public site is readable by anyone and would be a genuine vulnerability, unlike the current design.
